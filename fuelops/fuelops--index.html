Every shift, operators reach for a plastic wheel chart and a photocopied table to correct fuel gravity for temperature. Those tools have not changed in decades, and the digital alternatives were written by people who had not stood next to a hydrometer.

Field validation

The calculations were checked against the physical instruments and printed tables in daily use at an airport fuel facility, not only against the published formulas. Reference sources were the Gammon GTP-3012-1A wheel, ATA Form 103.08 fuel quality records, and printed compressibility factor tables.

Two corrections were found only because of that testing. Neither is obvious from the formulas alone.

Hydrometer glass expansion

Early results drifted low, and the drift grew as the temperature difference grew. The glass of the hydrometer itself expands with temperature, which changes the volume it displaces; API 11.1 corrects for this. Adding the correction closed the gap across the whole temperature range.

Weight in air against weight in vacuum

Metric density is defined in vacuum, but the API pounds-per-gallon tables report weight in air. Subtracting air buoyancy of 0.0011 g/mL brought the figure into agreement with the field records. The difference is 0.009 lb/gal — small enough to look like a rounding artefact, large enough that any operator checking the app against their chart would have called it a bug.

A third detail came out of the same testing. Displayed values are now derived from the rounded corrected API rather than from the internal high-precision figure. That shifts specific gravity by 0.001, which is invisible to the physics, but it means every number on screen agrees with every other number on screen and with the operator's wheel.

What it does

API gravity correction

The digital equivalent of the wheel: observed API and fuel temperature give corrected API at 60°F, with density, specific gravity, and pounds per gallon alongside. Switchable between ASTM 5B/6B referenced to 60°F and ASTM 54B referenced to 15°C.

Compressibility factor

Replaces the printed compressibility tables used in fuel cart and meter calibration. Because it implements API MPMS 11.2.1 directly rather than reading a grid, it accepts any input instead of the 0.5-step increments a printed page is limited to, and covers the full 0 to 90 degree API range instead of the narrow band that fits on one sheet.

Meter calibration factor

The inverse operation, for calibration technicians: corrected API and product temperature give the correction factor, with density and pounds per gallon at that temperature.

Unit converter and saved records

Volume, weight, temperature, and length conversion, plus a density-bridged converter between volume and mass. Calculations can be tagged with a tank or cart number and stored on the device, so a field reading survives until it reaches the paper form.

The calculation

  • Iterative convergence. Standard density is needed to find the thermal expansion coefficient, but the coefficient is needed to find standard density. ASTM resolves the circularity by iterating to a tolerance rather than making a single pass, and so does this.
  • Constants selected inside the loop. The K₀ and K₁ coefficients differ by fuel class — gasolines, transition, jet fuels and kerosene, diesels. Selecting them inside the iteration means a density that crosses a class boundary during convergence still lands on the right constants.
  • Real 6B constants for the US standard. The constants referenced to 60°F are the 15°C constants scaled by 5/9, since one Fahrenheit degree is 5/9 of a Celsius degree. An earlier version bridged the two references with an empirical fudge factor. It fitted the data but could not be defended, so it was removed.
  • Fuel type detection from the corrected API range.

How it is built

The app keeps an MVVM-style separation adapted to React Native conventions. Pure calculation and persistence live in /utils and /storage with no state and no interface. Custom hooks in /hooks take the ViewModel role, holding state, input parsing, validation, and orchestration. Screens and components are JSX only.

The unit converter is where that separation earns its keep: volume, weight, and length all run through one useUnitConverter hook driven by a unit table, so adding a category means adding a table rather than a screen.

Navigation is a custom drawer built on React Native's own Animated API. The usual choice, react-native-reanimated, kept producing TurboModule errors against the new Android architecture, so the dependency was dropped in favour of about eighty lines of first-party code.

Storage is AsyncStorage. Builds are produced with EAS Build.

Scope and limits

  • Field validation covers 44 to 47 degrees API, which is jet fuel. The diesel and AVGAS bands have not been checked against physical instruments, and I would not claim them until they have been.
  • Android only. An iOS build waits on Apple Developer enrolment.
  • No fuel specification limits yet — density, flash point, and freeze point per ASTM D1655, D975, and D4814 are on the list but not in the app.
  • No PDF export for shift handover yet.

The calculations are an engineering aid. They are not to be used as the sole basis for custody transfer, billing, or any safety-critical decision.

What I took from it

The most useful thing I learned was not a framework. It was that in engineering software the physics is the test suite. Twice the code ran cleanly, looked right, and was wrong, and both times what caught it was a number that felt off to someone who had stood next to the hydrometer. Unit tests would have passed.
